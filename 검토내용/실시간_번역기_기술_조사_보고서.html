1. 먼저 결론

가장 현실적인 첫 제품

브라우저에서 마이크를 받고, WebRTC 또는 WebSocket으로 음성을 전송하며, 백엔드가 클라우드 실시간 번역 세션과 임시 인증을 관리하는 구조가 적합하다. 한국어↔영어 MVP는 먼저 음성→번역 자막을 안정화한 뒤 번역 음성 재생을 추가하는 순서가 위험과 비용이 가장 낮다.

빠른 MVP Azure Speech Translation처럼 STT·번역·TTS가 연결된 관리형 서비스를 사용한다. 부품 조합이 적어 개발과 장애 분석이 단순하다.
자연스러운 음성 대화 OpenAI 또는 Azure의 전용 Realtime Translate 계열처럼 음성을 연속적으로 처리하는 모델을 실제 업무 음성으로 검증한다.
용어 통제와 교체 가능성 STT → 텍스트 번역 → TTS를 분리하면 각 단계의 벤더를 교체하고 용어집·번역 메모리·후처리를 적용하기 쉽다.
민감정보·오프라인 우선 SeamlessM4T 계열과 로컬 ASR/TTS를 검토할 수 있지만 GPU, 배포, 모델 최적화와 품질 검증 비용이 크게 증가한다.

중요: 실제 서비스는 HTML 파일 하나만으로 안전하게 만들 수 없다.

정적 HTML에 장기 API 키를 넣으면 누구나 개발자 도구에서 키를 복사할 수 있다. 최소한 세션 생성, 임시 토큰 발급, 사용량 제한, 감사 로그를 담당하는 백엔드가 필요하다.

2. “실시간 번역기”의 범위부터 정의해야 한다

실시간이라는 표현은 하나의 기술이 아니라 서로 다른 지연·정확도 목표를 가진 제품군이다. 시작 전에 아래 결과물 중 무엇이 필요한지 정해야 아키텍처와 비용을 올바르게 고를 수 있다.

제품 형태 입력 출력 난이도 핵심 위험
실시간 자막 음성 같은 언어 텍스트 낮음 고유명사와 숫자 인식
번역 자막 음성 다른 언어 텍스트 중간 부분 문장 번역이 계속 뒤집힘
순차 통역 한 발화 단위 음성 번역 텍스트·음성 중간 침묵 감지와 턴 전환
동시 통역 연속 음성 겹쳐 나오는 번역 음성 높음 문장 후반 정보와 낮은 지연의 충돌
양방향 대화 두 사람의 음성 각 상대 언어의 음성 매우 높음 화자·언어·에코·동시 발화 구분

권장 첫 범위

한국어↔영어, 한 번에 한 명이 말하는 환경, 마이크 입력, 번역 자막 표시, 선택적 TTS 재생으로 제한한다. 회의 전체 동시통역과 다중 화자는 2단계 이후로 미룬다.

3. 핵심 처리 파이프라인

1. Capture 마이크 권한, 장치 선택, 에코 제거, 샘플링
2. Segment VAD, 잡음 억제, 발화 시작·종료 검출
3. Recognize 스트리밍 STT, 부분 결과와 최종 결과
4. Translate 문맥·용어집·문장 안정화·번역
5. Present 자막 교체, TTS 재생, 기록·다운로드

3.1 음성 수집

브라우저는 navigator.mediaDevices.getUserMedia({ audio: true })로 사용자의 허가를 받아 MediaStream을 얻는다. 일반 배포 환경에서는 HTTPS가 필요하며, 사용자에게 녹음 상태와 중지 수단을 명확히 보여야 한다.

3.2 전처리와 발화 검출

  • AEC: 스피커로 재생한 번역 음성이 다시 마이크로 들어가는 에코를 줄인다.
  • Noise suppression: 팬, 키보드, 도로 소음처럼 지속적인 배경음을 억제한다.
  • AGC: 너무 작거나 큰 음량을 일정 범위로 맞춘다.
  • VAD: 사람이 말하는 구간과 침묵을 분리해 API 호출량과 지연을 조절한다.

브라우저 기본 오디오 제약으로 시작하고, 더 정교한 PCM 변환이나 자체 VAD가 필요할 때 메인 UI 스레드를 막지 않는 AudioWorklet을 사용한다.

3.3 스트리밍 STT

스트리밍 인식은 말이 끝날 때까지 기다리지 않고 부분 결과(interim/partial)를 보낸다. 부분 결과는 빠르지만 수정될 수 있다. 최종 결과(final)는 상대적으로 안정적이므로 저장, 번역 확정, 감사 로그는 최종 결과를 기준으로 해야 한다.

3.4 기계 번역

짧은 조각을 즉시 번역하면 빠르지만 한국어의 서술어, 부정, 높임말처럼 문장 뒤에서 의미가 확정되는 요소 때문에 오역이 늘어난다. 따라서 화면에서는 빠른 임시 번역과 확정 번역을 시각적으로 구분하고, 발화가 끝나면 문맥을 포함해 재번역하는 방식이 실용적이다.

3.5 TTS와 재생

번역 음성은 완성 문장 전체를 기다리면 자연스럽지만 느리고, 작은 조각을 즉시 합성하면 빠르지만 억양이 끊긴다. 첫 버전에서는 자막을 먼저 보여주고 최종 문장 단위로 TTS를 재생하는 하이브리드가 좋다. 양방향 대화에서는 헤드셋 권장 또는 재생 중 마이크 감쇠가 필요하다.

4. 브라우저에서 사용할 기술

MediaDevices.getUserMedia 마이크 스트림을 얻는 표준 API. HTTPS 또는 localhost 같은 안전한 컨텍스트와 사용자의 명시적 권한이 필요하다.
Web Audio API / AudioWorklet 오디오 레벨 표시, 리샘플링, PCM 프레임 생성과 저지연 사용자 정의 처리를 수행한다.
WebRTC 브라우저 음성 통신에 적합하다. 미디어 전송, 네트워크 적응, 지터 처리 등 실시간 기능을 활용할 수 있다.
WebSocket 직접 만든 PCM/Opus 청크와 JSON 이벤트를 양방향으로 전송하기 좋다. 대신 오디오 버퍼링과 재연결 정책을 애플리케이션이 더 많이 책임진다.

WebRTC와 WebSocket 선택

기준 WebRTC WebSocket
적합한 상황 브라우저 음성 입출력, 낮은 지연, 양방향 음성 서버 중심 처리, PCM 제어, 이벤트 파이프라인
오디오 처리 브라우저와 연결 계층이 많은 부분을 처리 청크 크기, 인코딩, 버퍼를 직접 관리
이벤트 제어 DataChannel을 병행할 수 있음 JSON과 바이너리를 한 연결에서 명시적으로 관리
권장 전용 Realtime API가 WebRTC를 제공하면 우선 검토 여러 STT·번역기를 조합하는 서버 파이프라인에 적합

Web Speech API는 어디까지 쓸 수 있는가

Web Speech API는 SpeechRecognition과 SpeechSynthesis를 제공한다. 설치 없이 데모를 만들기에는 편하지만 인식 구현과 동작이 브라우저·운영체제에 따라 다르고, 일부 환경에서는 서버 기반 인식이 사용될 수 있다. 지원 범위, 연속 인식, 로컬 처리 기능은 브라우저별 검증이 필요하므로 상용 크로스브라우저 번역기의 핵심 엔진으로 고정하지 않는 것이 좋다.

활용 범위: 무키(keyless) 프로토타입, UI 흐름 검증, TTS 보조 기능. 정확도 SLA와 동일한 사용자 경험이 필요한 운영 서비스에는 관리형 API 또는 자체 백엔드가 안전하다.

5. 아키텍처 선택: 분리형과 직접 번역형

5.1 분리형(cascade)

Browser microphone
  └─ WebRTC / WebSocket
      └─ Backend gateway
          ├─ Streaming STT → source partial/final text
          ├─ Translation → target partial/final text
          ├─ Terminology / policy / post-processing
          └─ TTS → translated audio
              └─ Browser captions + playback

각 단계의 결과를 볼 수 있어 디버깅, 용어집, 금칙어, 저장, 벤더 교체가 쉽다. 반면 단계마다 네트워크와 처리 지연이 누적되며, STT 오류가 번역까지 전파된다.

5.2 직접 음성 번역(end-to-end)

Browser microphone
  └─ WebRTC realtime session
      └─ Speech translation model
          ├─ translated audio stream
          └─ translated transcript
              └─ Browser playback + captions

연속 음성을 직접 처리하는 모델은 연결 단계가 적고 자연스러운 말투와 낮은 체감 지연을 목표로 할 수 있다. 반면 중간 단계 통제, 용어 강제, 오류 원인 분석과 벤더 교체가 어려울 수 있다.

이 프로젝트에 권장하는 기준 아키텍처

  1. 1차: 분리형 또는 Azure Speech Translation으로 한국어↔영어 번역 자막 구현
  2. 2차: 최종 문장 단위 TTS와 용어집 추가
  3. 비교 실험: 동일 음성 평가 세트로 전용 Realtime Translate 모델과 체감 지연·정확도 비교
  4. 선정: 평균 점수가 아니라 고유명사, 숫자, 소음, 끼어들기 실패율로 최종 결정

6. 주요 기술·서비스 비교

아래 표는 기능 구조를 비교한 것이다. 언어·리전·모델·가격은 변할 수 있으므로 구현 직전 링크된 공식 문서에서 다시 확인해야 한다. 특히 “실시간 번역”이라는 말은 음성 스트리밍 자체를 뜻하기도 하고, 짧은 텍스트 요청에 즉시 응답한다는 뜻으로도 쓰인다.

선택 판단표

  • 한 공급자로 빠르게: Azure Speech Translation 우선 PoC
  • 음성의 자연스러움과 대화 경험: 전용 Realtime Translate 계열 병행 평가
  • 제조·의료·사내 용어의 강제: 분리형 + glossary/phrase hint
  • 현재 AWS/GCP 운영팀과 IAM을 그대로 활용: 해당 클라우드의 분리형 조합
  • 망 분리·데이터 외부 전송 금지: 자체 모델과 온프레미스 추론 가능성 조사

7. 지연시간 설계

“실시간”은 단일 숫자가 아니다. 사용자가 말한 시점부터 첫 글자가 보이는 시간, 문장이 확정되는 시간, 번역 음성이 시작되는 시간을 각각 측정해야 한다.

Time to First Partial 첫 임시 전사·번역이 보일 때까지
Time to Final Text 발화 종료 후 확정 자막까지
Time to First Audio 번역 음성 재생이 시작될 때까지

실무 목표의 예

아래 수치는 공급자의 보장 수치가 아니라 초기 제품 목표를 세우기 위한 권장 예시다. 실제 네트워크, 언어쌍, 말의 길이와 모델에 맞춰 p50과 p95를 따로 측정한다.

구간 초기 목표 예시 주요 조정 수단
캡처·청크 50~200 ms 단위 청크 크기, PCM/Opus, AudioWorklet
네트워크 왕복 가까운 리전에서 p95 추적 리전, WebRTC, 재사용 연결
첫 임시 자막 체감상 1초 안팎 목표 VAD 민감도, 낮은 지연 모델
발화 후 최종 자막 약 1~2초 이내 목표 침묵 종료 임계값, 문장 경계
번역 음성 시작 짧은 문장 기준 약 2초 내외 목표 문장 분할, 스트리밍 TTS, 선행 버퍼

청크 크기의 트레이드오프

  • 너무 작으면 메시지 수와 프로토콜 오버헤드가 증가한다.
  • 너무 크면 첫 결과가 늦고 네트워크 손실 시 복구 단위가 커진다.
  • AWS 공식 가이드는 PCM 스트리밍 청크를 50~200 ms로 권장한다.
  • 16 kHz, 16-bit, mono PCM은 음성 인식에서 데이터량과 품질의 실용적 출발점이다.
  • 사용하는 API가 24 kHz 등 특정 입력 형식을 요구하면 그 형식이 우선한다.

부분 결과를 그대로 누적하면 안 되는 이유

부분 결과는 “오늘 계약을” → “오늘 계약은”처럼 이전 텍스트를 수정할 수 있다. 단순히 문자열 끝에 붙이면 중복과 오역이 생긴다. 이벤트의 발화 ID와 상태를 기준으로 동일 항목의 임시 텍스트를 교체하고, final 이벤트에서만 확정 목록에 넣어야 한다.

8. 정확도와 번역 품질 설계

STT 오류는 번역 단계에서 확대된다

“15 나노”를 “50 나노”로 인식하거나 제품명을 일반 단어로 바꾸면 번역 모델이 문장을 자연스럽게 다듬어 오히려 오류를 발견하기 어려워진다. 따라서 원문 전사와 번역문을 함께 표시하고, 숫자·단위·고유명사를 별도 평가해야 한다.

정확도를 높이는 실무 장치

  • 언어 힌트: 가능한 경우 입력 언어 또는 후보 언어를 세션에 명시한다.
  • 용어 힌트: 제품명, 사람 이름, 약어, 공정명, 고객 코드를 STT에 제공한다.
  • 용어집: 번역 단계에서 특정 원문이 항상 지정 번역으로 나오게 한다.
  • 문맥 창: 직전 확정 발화 몇 개를 번역 컨텍스트로 유지한다.
  • 표시 규칙: 임시 결과는 흐리게, 확정 결과는 선명하게 표시한다.
  • 재번역: 발화 종료 시 전체 문장과 앞 문맥을 이용해 최종 번역을 다시 만든다.
  • 신뢰도 정책: 낮은 신뢰도 숫자나 이름은 강조하거나 사용자 확인을 요청한다.

자동 언어 감지의 함정

짧은 감탄사, 숫자, 외래어만으로는 언어를 안정적으로 구분하기 어렵다. 언어가 고정된 제품은 자동 감지보다 사용자가 언어쌍을 선택하게 하는 편이 빠르고 정확하다. 코드 스위칭이 필수인 경우에만 다국어 인식 기능과 전환 비용을 평가한다.

동시통역의 근본적 문제

한국어와 영어는 어순이 달라 번역 모델이 문장 끝을 기다려야 정확해지는 경우가 많다. 기다리면 정확하지만 느리고, 먼저 말하면 빠르지만 이후 내용을 보고 번역을 되돌려야 한다. 제품은 “낮은 지연”과 “안정된 번역” 중 어디에 무게를 둘지 명시해야 한다.

9. 데이터 모델과 이벤트 처리

벤더가 바뀌어도 UI가 유지되도록 애플리케이션 내부 이벤트를 공급자 응답과 분리한다. 최소 단위는 세션, 발화, 부분 결과, 최종 결과, 오류, 사용량이다.

필수 상태

  • idle: 마이크를 사용하지 않음
  • requesting_permission: 사용자 응답 대기
  • connecting: 세션과 미디어 연결 생성 중
  • listening: 음성 수집 중
  • reconnecting: 짧은 장애 복구 중
  • stopped: 사용자가 정상 종료
  • failed: 자동 복구 불가, 구체적인 원인 표시

이벤트 처리 규칙

  1. 발화별 ID로 부분 결과와 최종 결과를 연결한다.
  2. 순서가 뒤바뀔 수 있으므로 로컬 수신 순서만 믿지 않는다.
  3. 부분 결과는 같은 행을 교체하고, 확정 결과만 대화 기록에 추가한다.
  4. 재연결 뒤에는 세션 ID와 발화 ID 충돌을 방지한다.
  5. 오래된 부분 결과가 늦게 도착해 최종 문장을 덮지 못하게 한다.
  6. 오디오 재생 큐는 자막 큐와 분리하고 취소·끼어들기를 지원한다.

10. 보안과 개인정보

장기 API 키는 브라우저에 두지 않는다.

소스 코드 난독화나 환경 변수 이름 변경으로는 브라우저에 전달된 비밀을 보호할 수 없다. 백엔드가 표준 키를 보관하고, 브라우저에는 짧게 살아 있는 임시 세션 자격만 전달한다.

권장 인증 흐름

  1. 사용자가 애플리케이션에 로그인한다.
  2. 브라우저가 백엔드에 번역 세션 생성을 요청한다.
  3. 백엔드는 사용자 권한, 언어쌍, 할당량과 차단 상태를 검사한다.
  4. 백엔드가 공급자의 임시 토큰 또는 보호된 세션을 생성한다.
  5. 브라우저는 임시 자격으로 WebRTC/WebSocket을 연결한다.
  6. 백엔드는 사용 시간, 오류, 비용 관련 메타데이터를 기록한다.

개인정보 최소화

  • 원본 음성을 저장하지 않는 것을 기본값으로 하고 필요할 때만 명시적 동의를 받는다.
  • 전사 기록 저장 여부, 보관 기간, 삭제 방법을 사용자에게 알린다.
  • 민감정보가 포함될 수 있으면 로그에서 원문과 번역문을 마스킹하거나 제외한다.
  • 리전, 데이터 보존, 모델 개선 사용 여부, 하위 처리자를 공급자 계약에서 확인한다.
  • TLS, 최소 권한 IAM, 서버 측 비밀 저장소, 요청 속도 제한을 적용한다.
  • 마이크가 활성화된 동안 명확한 시각 표시와 즉시 중지 버튼을 제공한다.

브라우저 보안 조건

마이크 API는 안전한 컨텍스트가 필요하다. 로컬 개발의 localhost와 달리 실제 네트워크 주소의 평문 HTTP에서는 동작하지 않을 수 있으므로 배포 환경에 HTTPS를 준비한다. iframe에서 사용할 경우 Permissions-Policy와 allow="microphone" 범위도 최소화한다.

남용과 비용 폭주 방지

  • 사용자별 동시 세션 수와 일일 분량 제한
  • 무음이 긴 세션 자동 종료
  • 임시 토큰의 짧은 만료 시간과 일회성 세션 연결
  • 비정상 재연결·실패 반복에 지수 백오프
  • 분당 사용량, 실패율, 평균 세션 길이, 비용 추정치 알림

11. 품질과 운영 검증 방법

평가 데이터

깨끗한 스튜디오 음성만으로 평가하면 실제 품질을 과대평가한다. 최소 100~300개 발화를 업무 도메인별로 만들고, 사람이 확인한 원문과 번역 기준문을 함께 보관한다.

평가 축 반드시 포함할 사례 측정 예
음성 인식 남녀 화자, 억양, 빠른 말, 작은 목소리, 숫자·단위 WER/CER, 숫자 정확도, 누락률
번역 부정, 존댓말, 생략 주어, 긴 문장, 전문용어 COMET 계열 + 이중언어 사람 평가
지연 짧은 발화, 긴 발화, 침묵, 느린 네트워크 첫 부분·최종·첫 음성의 p50/p95
안정성 네트워크 끊김, 마이크 교체, 탭 백그라운드 복구 성공률, 중복·유실 발화율
사용성 권한 거부, 무음, 잘못된 언어, 중지 후 재시작 과업 성공률, 사용자 수정 횟수
비용 1분·10분·1시간, 1개·2개 대상 언어 유효 음성분당 비용, 세션당 비용

운영 지표

  • 세션 생성 성공률과 연결 시간
  • 첫 부분 결과, 최종 자막, 첫 번역 음성의 p50/p95/p99
  • 빈 전사, 잘린 전사, 늦게 도착한 전사 비율
  • 사용자가 언어를 재선택하거나 번역을 수정한 비율
  • 공급자 오류 코드별 발생률과 재시도 성공률
  • 분당 처리 비용과 무음에 낭비된 처리 시간

출시 전 최소 통과 조건 예시

  • Chrome과 Edge 최신 버전에서 마이크 권한 허용·거부·재허용 흐름이 정상이다.
  • 한국어↔영어 100개 기준 발화에서 숫자·단위·제품명 결과를 사람이 확인했다.
  • 부분 결과가 최종 결과를 덮거나 중복 저장하는 현상이 없다.
  • 네트워크를 잠시 끊었다 복구해도 무한 재연결과 중복 과금이 발생하지 않는다.
  • 브라우저 번들, HTML, 네트워크 응답에 장기 API 키가 노출되지 않는다.
  • 세션 종료 시 마이크 트랙과 연결이 실제로 닫힌다.
  • 0건·빈 전사·번역 실패를 성공으로 표시하지 않는다.

12. 권장 구현 로드맵

단계 0 — 제품 조건 확정

  • 언어쌍: 한국어↔영어부터 시작할지
  • 사용 환경: 1:1 대화, 회의, 전화, 강의 중 무엇인지
  • 출력: 자막만 또는 번역 음성까지 필요한지
  • 데이터: 음성과 전사를 저장할지, 저장 금지인지
  • 목표: 지연, 품질, 월 예산과 동시 사용자 수

단계 1 — 마이크와 원문 자막 PoC

마이크 권한, 입력 레벨, 시작·중지, 부분·최종 STT만 구현한다. 번역 전에 실제 환경에서 고유명사와 숫자 인식이 충분한지 확인한다.

단계 2 — 번역 자막 MVP

언어쌍 선택, 최종 문장 번역, 임시/확정 표시, 최근 대화 문맥, 오류 상태를 추가한다. 이 단계가 사용자 가치와 핵심 품질을 가장 저렴하게 검증한다.

단계 3 — 용어집과 번역 음성

업무 용어집, 숫자·단위 보호, 최종 문장 TTS, 재생 큐와 음소거를 추가한다. 헤드셋 없이 사용할 경우 에코와 재인식 여부를 별도 시험한다.

단계 4 — 운영 안전장치

로그인, 임시 토큰, 할당량, 비용 알림, 구조화 로그, 재연결, 데이터 보존 정책과 사용자 삭제 기능을 넣는다.

단계 5 — 고급 기능

자동 언어 감지, 다중 화자, 화자 분리, 동시통역, 모바일 최적화, 자체 모델은 사용 사례와 실패 데이터가 쌓인 뒤 각각 독립 실험으로 진행한다.

권장 다음 산출물

실제 구현에 들어갈 때는 먼저 “한국어↔영어 1:1 번역 자막”의 화면 시안, 기술 공급자 1개, 데이터 저장 여부와 성공 기준을 확정한 후 프로젝트 구조를 만든다.
