1. 최종 추천

추천안: Azure 기반의 참가자별 분리형 실시간 번역

각 참가자의 음성 스트림을 분리해 Azure AI Speech로 전사하고, 확정된 원문을 Azure Translator로 필요한 대상 언어에 병렬 번역한다. 결과는 SignalR 또는 WebSocket으로 각 참가자에게 전달해 본인이 선택한 언어의 자막을 표시한다.

회의 음성 Teams 사용 시 Microsoft Graph 실시간 미디어 봇을 우선 검토한다. 다른 플랫폼은 공식 SDK·봇 또는 참가자별 클라이언트 어댑터를 사용한다.
음성 인식 Azure AI Speech 실시간 STT를 참가자별 스트림에 적용한다. 중간 자막과 확정 자막을 구분한다.
번역 Azure Translator Text API로 원문 1개를 필요한 언어들에 병렬 번역한다. 회사 용어는 별도 용어 계층에서 통제한다.
사용자 전달 ASP.NET Core와 SignalR로 참가자별 선택 언어 자막을 전달한다. TTS는 기본값이 아닌 개인 선택 기능으로 둔다.

왜 이 방식인가?

네 언어를 모두 지원하면서 원문 전사, 번역, 화자, 용어집, 보안과 오류 원인을 각각 확인할 수 있다. 회의 중 여러 사람이 서로 다른 언어를 쓰더라도 참가자 단위로 입력을 분리하면 자동 언어 감지와 화자 분리의 불확실성을 크게 줄일 수 있다.

번역 음성보다 번역 자막을 우선한다.

회의 전체에 번역 음성을 재생하면 원래 발언과 겹치고, 마이크로 다시 유입되어 재인식되는 문제가 생긴다. 첫 버전은 자막 중심으로 만들고, 번역 음성은 개인 헤드셋에서 요청했을 때만 재생하는 것이 안전하다.

2. 글로벌 회의 사용 조건

일반 통역 앱과 달리 사내 회의 번역기는 다중 참가자, 여러 언어, 업무 용어, 기밀정보와 회의 플랫폼 통합을 동시에 다뤄야 한다. 다음 조건을 기준 설계로 삼는다.

구분 기준 조건 설계 영향
사용자 사내 임직원과 승인된 외부 참석자 SSO, 권한, 외부 사용자 정책 필요
언어 한국어·영어·중국어(보통화)·베트남어 4개 입력 locale과 사용자별 출력 언어 관리
환경 온라인 회의와 하이브리드 회의 회의 플랫폼 음성과 회의실 음향을 구분
출력 실시간 번역 자막 중심 부분·확정 자막 UI와 지연 관리
업무 데이터 제품명, 고객명, 약어, 숫자, 일정 STT 힌트와 다국어 용어집 필수
보안 기밀 회의 가능 저장 최소화, 감사, 리전·보존 정책 검토

권장 1차 범위

  • 참가자는 회의 입장 시 자신의 주 사용 언어와 자막 언어를 선택한다.
  • 한 참가자가 한 번에 한 언어를 사용하는 것을 기본으로 한다.
  • 동시에 여러 사람이 말할 때는 참가자별 스트림 또는 플랫폼 메타데이터로 구분한다.
  • 원문과 번역문을 함께 표시해 숫자·이름 오류를 발견할 수 있게 한다.
  • 회의 녹음과 전체 전사 저장은 기본으로 끄고 별도 승인을 받는다.

3. 대상 언어 지원과 코드

한국어 STT ko-KR · 번역 ko
영어 STT en-US · 번역 en
중국어 STT zh-CN · 번역 zh-Hans
베트남어 STT vi-VN · 번역 vi

Azure Speech의 실시간 음성 인식은 ko-KR, en-US, zh-CN, vi-VN을 지원하며, 표준 Speech Translation의 번역 대상 텍스트 언어에도 한국어, 영어, 중국어 간체와 베트남어가 포함된다.

중국어 범위를 명확히 해야 한다.

이 문서는 중국 본토의 보통화와 간체 자막을 기본값으로 하여 zh-CN과 zh-Hans를 추천한다. 광둥어 또는 번체 중국어가 필요하면 zh-HK, zh-TW, zh-Hant를 별도 언어로 시험하고 UI 선택지를 분리해야 한다.

왜 언어 코드를 두 종류로 관리하는가

STT는 발음과 지역 억양을 구분하기 위해 전체 locale을 사용하고, 번역 API는 주로 언어 코드 또는 문자 체계를 사용한다. 내부 설정에서 speechLocale과 translationLanguage를 별도 필드로 보관해야 실수하기 어렵다. 

const LANGUAGES = {
  ko: { speechLocale: "ko-KR", translationLanguage: "ko" },
  en: { speechLocale: "en-US", translationLanguage: "en" },
  zh: { speechLocale: "zh-CN", translationLanguage: "zh-Hans" },
  vi: { speechLocale: "vi-VN", translationLanguage: "vi" }
};

5. 회의 음성 수집 방식

번역 모델보다 먼저 결정해야 하는 것이 음성 입력 경로다. 원격 참가자의 음성을 받지 못하면 마이크 번역 데모는 가능해도 실제 글로벌 회의 번역기는 될 수 없다.

방식 장점 제약 권장도
Teams 미디어 봇 회의에 정식 참가하여 실시간 미디어와 회의 상태를 처리 C#/.NET, Azure 배포, 공개 연결, 운영 복잡도 Teams 운영 추천
참가자별 번역 클라이언트 각 사용자 마이크가 분리되어 언어·화자 처리가 쉬움 모든 참가자가 앱을 실행해야 하고 원격 음성 공유 구조 필요 PoC 추천
브라우저 화면·시스템 오디오 캡처 빠른 실험, 기존 회의 앱 변경이 적음 권한 팝업, 브라우저·OS 차이, 화자 메타데이터 부족 임시 PoC
회의실 혼합 마이크 물리 회의실 전체 음성을 한 입력으로 처리 화자 분리와 중첩 발화 품질 저하 보조 경로

Teams 미디어 봇의 기술적 주의점

  • 공식 application-hosted media bot 경로는 C#/.NET을 요구한다.
  • 운영 봇은 Azure의 Windows Server 환경에 배포해야 하는 조건이 있다.
  • Azure Web App에 단순 배포하는 형태가 아니며 VM, VMSS, AKS 등의 운영 설계가 필요하다.
  • 미디어 호출은 이를 수락한 VM 인스턴스에 고정되므로 세션 중 VM 종료를 피해야 한다.
  • 미디어 SDK 버전을 지속적으로 최신 상태에 가깝게 유지해야 한다.
  • 개발자 미리 보기 상태인 항목은 구현 시점의 공식 문서를 다시 확인해야 한다.

단순 웹 페이지의 한계

getUserMedia()는 기본적으로 사용자의 로컬 마이크를 가져온다. 회의 앱에서 들리는 원격 참가자 전체 음성을 자동으로 제공하지 않는다. 화면 공유 기반 시스템 오디오 캡처는 사용자 선택과 플랫폼 지원에 의존하므로 장기 운영의 핵심 경로로 삼지 않는 것이 좋다.

6. 언어 식별과 화자 처리

추천 우선순위

  1. 참가자 프로필: 회의 입장 시 본인이 말할 언어를 선택한다.
  2. 참가자별 스트림: 플랫폼이 제공하는 참가자·스트림 연결 정보를 사용한다.
  3. 자동 언어 식별: 참가자가 선택 언어와 다르게 말할 때의 보조 기능으로 사용한다.
  4. 혼합 음성 diarization: 참가자 스트림을 구할 수 없을 때의 최후 수단으로 둔다.

Azure Language Identification은 후보 언어 목록과 음성을 비교해 언어를 선택한다. continuous LID는 최대 10개 후보를 받을 수 있으므로 이 프로젝트의 4개 언어를 후보로 구성할 수 있다. 다만 LID를 켜면 초기 지연이 증가하고, 후보에 없는 언어가 들어와도 후보 중 하나를 반환하므로 결과를 절대적인 사실로 취급하면 안 된다. 

candidateSpeechLocales = [
  "ko-KR",
  "en-US",
  "zh-CN",
  "vi-VN"
];

현재 조합 제약:

Azure의 다중 채널 실시간 전사는 diarization을 지원하지만, 공식 문서상 다중 채널 모드에서 Language Identification과 multilingual models는 지원되지 않는다. 따라서 “혼합 또는 다중 채널 하나에 화자 분리와 4개 언어 자동 감지를 모두 켜면 된다”는 설계는 피한다.

권장 해결 방식

  • 가능하면 참가자별 모노 음성 스트림을 각각 STT 세션으로 처리한다.
  • 참가자의 언어 설정을 STT locale로 사용해 속도와 정확도를 높인다.
  • 언어가 자주 바뀌는 사용자에게만 continuous LID 세션을 허용한다.
  • 플랫폼 참가자 ID를 화자 이름과 연결하고 음성 생체정보 기반 신원 확인은 하지 않는다.
  • 여러 사람이 동시에 말하면 각 스트림은 처리하되 UI에서 중첩 발화를 별도 표시한다.

7. 권장 실시간 번역 처리 흐름

1. 회의 입력
Teams 미디어 봇 또는 플랫폼 어댑터가 참가자별 음성 스트림과 참가자 ID를 수신한다.
2. 음성 인식
참가자의 설정 언어로 Azure Speech 세션을 열고 partial·final 원문 전사를 생성한다.
3. 문장 안정화
부분 결과는 임시 자막으로 표시하고 final 결과만 기록·최종 번역 대상으로 확정한다.
4. 용어 보호
제품명, 조직명, 고객명, 코드와 숫자를 탐지해 사내 용어 규칙을 적용한다.
5. 번역 fan-out
원문 언어를 제외한 최대 3개 대상 언어로 병렬 번역하고 캐시한다.
6. 사용자 전달
SignalR 그룹으로 참가자별 선택 언어의 원문·번역·화자·시간 정보를 전송한다.
7. 선택적 TTS
요청한 사용자에게만 번역 음성을 합성해 개인 헤드셋으로 재생한다.
[Teams / Meeting Platform]
            │ participant audio + participant ID
            ▼
  [Media Ingestion Adapter]
            │ one logical stream per speaker
            ▼
      [Azure AI Speech]
      partial / final transcript
            │
            ▼
 [Terminology & Policy Layer]
            │
            ▼
      [Azure Translator]
       ko / en / zh / vi
            │
            ▼
  [SignalR Caption Gateway]
       ├─ Korean caption group
       ├─ English caption group
       ├─ Chinese caption group
       └─ Vietnamese caption group

왜 Speech Translation 하나로 끝내지 않는가

Azure Speech Translation은 빠른 PoC에는 매우 좋다. 그러나 글로벌 회의 운영에서는 하나의 원문을 여러 참가자 언어에 재사용하고, 원문·번역·화자·용어 처리와 비용을 각각 관찰해야 한다. STT와 Translator를 논리적으로 분리하면 다음 이점이 있다.

  • 원문 전사를 한 번만 생성하고 필요한 번역 결과를 캐시할 수 있다.
  • 참가자가 중간에 자막 언어를 변경해도 확정 원문에서 다시 번역할 수 있다.
  • STT 오류와 번역 오류를 분리해 분석할 수 있다.
  • 업무 용어를 번역 전에 보호하거나 번역 후 검사할 수 있다.
  • 향후 특정 언어쌍만 다른 번역 엔진으로 교체하기 쉽다.

부분 번역 정책

  • 빠른 체감을 위해 안정도가 높은 partial만 임시 번역한다.
  • 임시 번역은 흐린 색으로 표시하고 계속 누적하지 않고 같은 발화 행을 교체한다.
  • final 원문이 오면 직전 문맥과 함께 다시 번역해 확정한다.
  • 발화 ID와 sequence 번호로 늦게 도착한 이벤트가 final을 덮지 못하게 한다.

8. 사내 용어와 번역 품질

글로벌 회의에서 체감 품질을 가장 크게 떨어뜨리는 것은 일반 문장이 아니라 회사명, 제품명, 공정명, 고객사, 조직 약어, 숫자와 납기다. 범용 모델 교체보다 먼저 회사 용어 관리 체계를 구축하는 편이 효과적이다.

3단계 용어 처리

1. STT Phrase List 제품명과 약어가 소리에서 원문 텍스트로 정확히 변환되도록 후보 용어를 제공한다.
2. 애플리케이션 용어 계층 원문에서 보호할 토큰을 찾아 번역 전후에 검증한다. 숫자·단위·부품번호도 함께 검사한다.
3. Custom Translator 충분한 승인 번역문과 회의 문장이 쌓인 언어쌍은 도메인 맞춤 번역 모델을 별도 평가한다.
4. 사람 피드백 임직원이 수정한 용어를 바로 모델에 넣지 않고 검토·승인·버전 관리 후 배포한다.

Dynamic Dictionary 제한

Azure Translator의 dynamic dictionary는 고유명사와 복합명사처럼 제한된 용도에 적합하며, 공식 문서상 영어와 다른 지원 언어의 조합을 요구한다. 따라서 한국어↔중국어, 한국어↔베트남어처럼 영어가 포함되지 않는 모든 조합을 이것 하나로 해결할 수 없다. 네 언어 전체에는 애플리케이션 용어 계층과 언어쌍별 검증이 필요하다.

권장 용어 데이터 구조

{
  "termId": "product-ax100",
  "type": "product_name",
  "doNotTranslate": true,
  "forms": {
    "ko": "AX100",
    "en": "AX100",
    "zh-Hans": "AX100",
    "vi": "AX100"
  },
  "speechHints": ["에이엑스 백", "AX one hundred"],
  "approvedBy": "language-admin",
  "version": 3
}

품질 우선순위

  1. 숫자, 날짜, 통화, 수량과 단위가 바뀌지 않아야 한다.
  2. 제품명, 고객명, 사람 이름과 조직 약어가 보존되어야 한다.
  3. 부정 표현과 확정·예상·검토 같은 업무 상태가 정확해야 한다.
  4. 문장이 자연스러운지는 의미 정확도 다음에 평가한다.

9. 회의 자막 화면의 필수 기능

내 말하기 언어 참가자가 현재 사용하는 입력 언어를 선택한다. 자동 감지는 선택 옵션으로 둔다.
내 자막 언어 각 참가자가 한국어, 영어, 중국어, 베트남어 중 하나를 독립적으로 선택한다.
원문 + 번역문 번역문을 크게 표시하되 원문을 함께 제공해 이름과 숫자를 비교할 수 있게 한다.
화자 표시 플랫폼 참가자 이름을 사용하고 불확실한 음성 기반 신원 추측은 하지 않는다.
임시·확정 상태 partial은 흐리게, final은 선명하게 표시하고 자막이 수정될 수 있음을 알린다.
보안 상태 번역 활성화, 저장 여부, 녹음 여부, 중지 버튼을 항상 보이게 한다.

접근성과 사용성

  • 색만으로 원문·번역·임시 상태를 구분하지 않고 텍스트 라벨을 함께 사용한다.
  • 글자 크기, 고대비, 자막 줄 수, 자동 스크롤을 사용자가 조절할 수 있게 한다.
  • 화면 읽기 도구에 final 자막만 과도하지 않게 전달하도록 live region을 설계한다.
  • 발언이 겹치면 화자별 열보다 시간순 카드가 모바일과 작은 창에서 읽기 쉽다.
  • 번역 실패 시 빈 화면이 아니라 원문과 명확한 오류 상태를 유지한다.

TTS 사용 정책

  • 회의 전체 스피커에는 기본적으로 재생하지 않는다.
  • 개인 헤드셋 사용자만 자신이 선택한 번역 음성을 들을 수 있게 한다.
  • 다음 발화가 시작되면 이전 번역 음성을 축약하거나 취소할 수 있게 한다.
  • 빠른 partial이 아니라 확정 또는 안정된 문장 조각만 합성한다.

10. 보안·개인정보·운영 기술

인증과 권한

  • Microsoft Entra ID SSO로 임직원과 외부 참석자를 구분한다.
  • 회의 생성자, 번역 사용자, 용어 관리자, 운영 관리자 역할을 분리한다.
  • 백엔드는 Managed Identity로 Azure 서비스에 접근하고 가능한 경우 정적 키를 없앤다.
  • 필요한 비밀은 Key Vault에 저장하며 웹 클라이언트에 서비스 키를 전달하지 않는다.

데이터 보존

Microsoft 공식 문서에 따르면 Azure의 실시간 Speech-to-Text는 음성을 서버 메모리에서 처리하며 저장소에 보관하지 않고, 실시간 STT와 Speech Translation에서 고객 제공 데이터를 보존하지 않는다고 설명한다. 그러나 애플리케이션이 별도로 저장하는 자막·로그·용어 데이터는 회사가 직접 보존 정책과 삭제 기능을 설계해야 한다.

화자 분리는 생체정보 관련 검토가 필요할 수 있다.

diarization은 화자 구분을 위해 음성 특성 신호를 분석한다. 플랫폼 참가자 ID로 화자를 연결할 수 있다면 이를 먼저 사용하고, 음성 기반 화자 분리를 활성화하기 전에는 법무·보안 검토와 참석자 고지·동의 절차를 확인한다.

저장 기본값

  • 원본 음성 저장: 기본 끔
  • 전체 원문·번역 저장: 기본 끔 또는 회의 주최자 정책 적용
  • 운영 로그: 원문을 제외한 세션 ID, 지연, 오류 코드, 사용량 중심
  • 용어 오류 피드백: 사용자가 명시적으로 제출한 문장만 별도 보관
  • 보존 기간 종료: 자동 삭제와 관리자가 확인할 수 있는 삭제 기록

관측 지표

  • 회의 참가 성공률과 미디어 연결 시간
  • 언어별 첫 partial, final, 번역 완료 지연의 p50·p95
  • 빈 전사, 중복 자막, 잘린 문장, 재연결 횟수
  • 언어쌍별 번역 호출량과 회의당 예상 비용
  • 용어 보호 실패, 숫자 변경, 사용자 수정 비율

  • 제품명 30개, 숫자·날짜·단위가 포함된 평가 문장 작성
  • Azure Speech Translation 단독과 STT + Translator 조합 비교

2단계 — 회의용 MVP

  • 입력 4개 언어와 사용자별 출력 4개 언어 선택

  • 원본 음성 비저장, 메타데이터 중심 로그

3단계 — 실제 회의 플랫폼 통합

  • Teams라면 application-hosted media bot의 별도 인프라 PoC
  • 회의 참가·퇴장, 참가자 ID, 동시 발화, 회의 종료 처리
  • 회의 30분·60분 지속성 및 VM 장애 복구 시험
  • 보안·법무·개인정보 검토와 참석자 고지

4단계 — 제한된 사내 파일럿

  • 언어별 원어민 임직원이 실제 업무 회의에서 품질 평가
  • 언어쌍별 오류와 수정 데이터를 용어 관리자에게 전달
  • 회의당 비용, 지연, 실패율, 사용자 만족도 측정
  • 보존 정책과 삭제 요청 절차 검증

5단계 — 운영 확장

  • 언어쌍별 품질 기준을 통과한 기능만 정식 제공

  • 용어 승인·배포·롤백 체계
  • 개인 헤드셋 TTS, 회의 요약 등은 별도 승인 후 추가

가장 먼저 검증할 것

UI보다 먼저 각 언어 원어민의 실제 회의 음성 30~60분을 확보해 STT 정확도, 숫자·제품명 오류, final 번역 지연을 측정한다. 이 결과가 기술 공급자와 용어 전략을 결정하는 가장 중요한 근거가 된다.

13. PoC와 운영 검증 기준

평가 데이터 구성

  • 각 언어 최소 100개 발화와 3명 이상의 화자
  • 깨끗한 헤드셋, 노트북 마이크, 회의실 스피커폰 음성
  • 제품명, 고객사, 조직 약어, 이메일, 숫자, 통화, 날짜, 단위 포함
  • 빠른 말, 억양, 침묵, 끼어들기, 두 사람 동시 발화 포함
  • 원어민이 확인한 원문과 번역 기준문
지표 측정 대상 권장 판정 방식
STT WER/CER 언어별 원문 전사 전체 평균과 언어·장치별 결과를 함께 보고
핵심 정보 정확도 숫자, 날짜, 단위, 제품명 항목별 exact match와 심각 오류 건수
번역 의미 정확도 12개 방향의 언어쌍 자동 지표와 원어민 5점 평가 병행
첫 partial 지연 발화 시작→첫 화면 표시 p50·p95, 언어별 분리
final 번역 지연 발화 종료→확정 번역 표시 p50·p95와 3초 초과율
운영 안정성 60분 회의와 네트워크 단절 유실·중복·재연결·세션 종료 오류
비용 STT 분·번역 문자·TTS 사용량 회의당·참가자당·언어당 실제 비용

출시 전 체크리스트

  • 4개 입력 언어와 12개 방향의 출력 언어쌍을 실제 음성으로 확인했다.
  • 중국어가 보통화·간체라는 범위를 사용자와 합의했다.
  • 참가자별 음성·언어·화자 연결이 틀어지지 않는다.
  • partial 이벤트가 final 자막을 덮거나 중복 저장하지 않는다.
  • 숫자·날짜·단위·제품명 심각 오류 기준과 대응 UI가 있다.
  • 회의 중 네트워크 장애 후 자동 복구와 중복 과금 방지가 동작한다.
  • 웹 클라이언트와 로그에 API 키나 토큰 원문이 노출되지 않는다.
  • 음성·자막 저장 여부와 보존 기간이 참석자에게 표시된다.
  • 회의 종료 후 마이크, 미디어 연결, STT 세션이 모두 닫힌다.
  • 빈 전사나 번역 0건을 성공으로 기록하지 않는다.
